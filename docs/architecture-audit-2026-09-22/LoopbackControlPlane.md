# Loopback control plane — one listener, six credential models

Methodology: [architecture-audit](../../.orgii/skills/architecture-audit/SKILL.md).

Branch audited: `feat/shared-ui-cli-rulebook` at `837ddd3828` (PR #1724, not yet
on `develop`). `api::ui_commands` exists only on that branch.

Scope: every credential mechanism reachable through
`src-tauri/src/api/server.rs::build_app`, plus the two surfaces that
deliberately sit outside it (`mobile_bridge`, and the IDE server's own
protected router as it stands after PRs #2052/#2053/#2054). Command
semantics, the `app_ui` broker's request lifecycle, the terminal adapter and
the frontend receiver are **out of scope** — they were audited on
2026-09-14 (see [prior coverage](#prior-coverage)).

Paths beginning `src/api/`, `crates/` and `src/agent_sessions/` are relative
to `src-tauri`; paths beginning `src/services/` are relative to the
repository root.

This audit is read-only. No source file was modified.

Two facts that the table cannot show and that shape everything below:

- **Authorization is not on this listener.** For #6 the HTTP boundary
  authenticates and nothing more; the capability tier (`ui.read`,
  `terminal.read`, `ui.present`, `terminal.write`) is enforced in the
  frontend receiver at `src/services/uiCommands/execute.ts:63-86`. The
  native `control_orgii` path reaches the same broker and the same receiver,
  so the two entry points agree — but a reviewer looking only at
  `ui_commands/mod.rs` sees no authorization at all and may conclude none
  exists.
- **The port is deterministic per install, not per launch.**
  `RuntimeInstanceProfile` derives `ide_server_port = 13847 + instance_id - 1`
  from the bundle identifier (`src/runtime_instance.rs:11-36`), and primary
  (`instance_id = 1`) and dev (`instance_id = 100`, port 13946)
  **deliberately share `~/.orgii`** because `default_orgii_home` returns
  `None` for both (`src/runtime_instance.rs:41-47`, applied at
  `src/app/bootstrap.rs:87-91`). Every credential file listed above is
  therefore written into a directory that more than one running app may own,
  at a port that is the same on every launch of the same install.

## 4. Migration proposal

The ordering constraint is that **no step may require all six surfaces to
change together**. Each step below is independently shippable and
independently verifiable.

**Step 0 — inventory guard (no production change).** The router test from
F2. It makes the current classification explicit and makes every later step
verifiable by diffing one test's expectations. Unblocks: everything, because
each subsequent step can then be reviewed as "this row moved from column A to
column B" instead of "trust me, I checked the router". Touches
`src/api/tests/` only.

**Step 1 — make the `ui_commands` sweep actually sweep (F1).** One module,
one test file. Option (a) from F1 — stable instance-keyed filename — is the
stronger fix because it removes the need for a sweep to be correct rather
than making the sweep correct. Unblocks: shipping PR #1724 without the
65-launch cliff, which is currently a release blocker. Must land before
step 3, because step 3's shared descriptor format should encode whichever
key wins here.

**Step 2 — one comparison helper (F4, F6).** Extract
`api::local_credential` with `verify_header_token` (over `subtle`) and
`is_loopback_host`, and move #1, #2, #6 and `mobile_bridge` onto it. Purely
internal: same headers, same tokens, same wire behaviour, and step 0's test
proves it. Unblocks step 4. Deliberately does **not** touch #4/#5, whose
comparisons are already correct and whose `Host` must stay unconstrained.

**Step 3 — one descriptor format (F3, F5, F7).** A single
`publish_descriptor(surface, port, token) -> io::Result<()>` owning atomic
create-0600 → write → `sync_all` → `rename`, the directory mode, the sweep,
and a versioned shape
`{schemaVersion, surface, instanceId, pid, port, token, startedAt}`. Migrate
`ui_commands` first (it is already closest), then `agent_status_ingest` to
`ORGII_HOME/endpoints/agent-status/<instance>.json` **while continuing to
write the legacy fixed path for one release** — hook subprocesses from
sessions that predate the change re-read that exact path on every invocation
(`status_post.rs:32-39`), so removing it in the same release strands live
sessions. Unblocks: F3's cross-instance collision, and makes the next
endpoint-file surface a call rather than a copy.

**Step 4 — authenticate by construction (F2's structural half).** Replace
the per-handler `if !authorized(...) { return denied(); }` in
`ui_commands/mod.rs:51-76` and `agent_status_ingest.rs:79-110` with a
`from_fn` layer per nested surface, exactly as `protected` already does at
`server.rs:346`. After this, adding a route under `/ui/v1` or `/hooks`
cannot produce an unauthenticated endpoint. This is the step that addresses
the _class_ of defect — the IDE server vulnerability and this audit both
exist because the guard was a thing each handler remembered rather than a
property of the router.

**Step 5 (optional, not recommended yet) — one credential model.** A single
process-wide token with per-surface scopes would collapse #1, #2 and #6.
It is not proposed here because the three have genuinely different
distribution channels — IPC to a webview, a file read by a short-lived
subprocess, a file read by a user-invoked CLI — and one token means one
compromise reaches all three. Revisit only if a fourth loopback surface
appears.

## Compatibility and rollback

This report adds one documentation file and changes no behaviour. Rollback
is deleting the file.

The migration it proposes is staged so that each step is independently
revertible. The only step with a compatibility obligation is Step 3: hook
subprocesses belonging to sessions started before the change re-read
`ORGII_HOME/session-provenance/status-endpoint.json` on every invocation,
so that path must keep being written for one release. Step 1's option (a)
changes the descriptor filename scheme; a CLI built before that change and
run against an app built after it finds no `<uuid>.json` matching its
`--instance` argument and reports `APP_NOT_RUNNING` rather than failing
loudly, which is worth a note in that PR's `Potential risks`.
