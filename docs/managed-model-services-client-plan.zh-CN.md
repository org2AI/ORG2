# 托管模型服务：ORG2 客户端实施计划

日期：2026-09-16。状态：已提交客户端实现，等待统一验收。按用户要求，本轮仅实现、阅读源码与格式化，未运行测试、类型检查、构建或 Computer Use。验收复选框保留未完成；实际协议、迁入范围与待测矩阵见 [客户端交接](managed-model-services-client-handoff.zh-CN.md)。

目标是让用户在 ORG2 中选择托管服务和模型，沿用正常会话流程开始使用，并能通过现有 App connections 在兼容的原生应用中使用同一授权。

## 1. 客户端验收标准

- [ ] 新用户没有已有服务或工作区记录，也可以完成登录、服务发现和首次使用。
- [ ] 普通模型选择器展示服务、模型、公开的可用状态和所需用户操作，不增加另一套独立选择器。
- [ ] 服务和模型列表来自服务器公开能力合同；新增兼容服务不需要重新发布桌面客户端。
- [ ] 一次启用 Package 即涵盖全部模型；切换模型不再次启用，所有启用套餐直接共用钱包余额。
- [ ] 不同服务来源使用稳定、不含秘密的引用；启动、继续、重启恢复和错误恢复都保留同一选择。
- [ ] 托管来源失效时明确提示恢复操作，不自动改用用户个人账号。
- [ ] 短时授权按需更新，长期凭据保存在操作系统凭据存储，不能进入 renderer、IPC 返回值或客户端配置文件。
- [ ] ORG2 的标准会话路径能够真实收发内容、调用本地工具、保存并重新打开对话。
- [ ] 兼容的 Claude Code、Claude Desktop 和 Codex 入口分别验证配置、启动、真实请求、冲突检测和恢复。
- [ ] 全量退出后本地路由失效；重启后可以恢复；仅关闭窗口与退出进程分别定义并验证。
- [ ] 托管服务接入不自动安装远程 Skill/MCP；用户自己配置的本地工具和 MCP 保持正常。
- [ ] 现有账号、已发布协议和历史配置仍可按原语义读取；新增能力采用显式版本协商。

## 3. 用户流程

### ORG2 内使用

1. 用户打开现有模型选择器，选择托管服务及该服务公开提供的模型。
2. 首次需要登录时走浏览器授权并返回 ORG2。授权成功回执与模型可用性是不同状态，不把“打开了链接”显示为“已连接”。
3. 首次启用时展示整个 Package 全部模型的公开价格区间及钱包扣费说明，一次确认启用全部模型；没有单模型启用或购买。模型选择只决定本次调用。服务端要求调整授权时仍整包确认，完成后回到原任务。
4. 服务端授权完成后，正常 session 创建流程保存来源引用和所选模型，由本地代理在需要时解析短时认证。
5. 后续消息、重新打开对话和应用重启从持久化 session 恢复来源；切换新会话的来源不会改写已经运行的会话。

服务不是一条伪造的个人 Key Vault 账号。个人账号仍使用原管理流程；托管连接由专门来源适配器提供给同一个模型选择器。

### 原生应用

App connections 复用已有连接卡片和编辑/恢复组件，显示所选服务、兼容模型和目标应用的真实状态。普通用户不填写 endpoint、复制 token 或下载凭据文件。

- 只配置用户选择的目标应用，使用已有事务及独立 profile 能力。
- Claude Code 的启动行为是打开相应终端；Claude Desktop 与 Codex 的应用行为各自验证。
- 客户端只通过本地代理使用动态认证；ORG2 需要保持运行。退出和恢复提示必须准确。
- 断开某个应用恢复它之前的配置，不等于退出整个托管账号或删除历史对话。
- 外部修改造成配置冲突时保留恢复/检查入口，不能覆盖外部编辑，也不能把冲突误报为版本不支持。

## 4. 公开协议与职责

| 信息/行为     | 客户端职责                                                                |
| ------------- | ------------------------------------------------------------------------- |
| 服务目录      | 读取服务稳定 ID、展示名、公开模型、可用状态与公开价格展示；不自行构造目录 |
| 使用授权      | 一次确认整个 Package 全部模型，共用一个 access 和预算；读取服务级确认状态，启用请求不含 model |
| 模型和能力    | 分开表达模型 ID、请求协议、目标客户端与能力；不能依赖名称前缀猜兼容性     |
| 来源持久化    | 存储版本号、连接引用、服务/access 引用、模型与执行目标；不保存上游凭据    |
| 认证          | 原生凭据模块管理长期授权；动态来源按需生成短时认证，仅供原生代理使用      |
| 使用/恢复结果 | 读取明确的结构化状态和可执行动作，不从错误字符串推断账户状态              |

拟定客户端来源结构表达 `kind`、`schema_version`、`connection_ref`、`service_id`、`access_ref`；模型、协议及目标按现有 session 分层保存。具体字段与公开 API schema 在第一批 contract fixtures 中一起定稿，Rust 与 TypeScript 同批更新。引用是标识，不应本身授予调用权限。

新接口与 IPC 应包括目录分页、未知版本处理和明确能力列表；不存在的模型、未知协议和不支持的客户端默认拒绝。客户端可以展示服务端提供的公开报价及确认动作，不包含服务器端的价格计算策略。

保留已发布 v1 的消息含义。新的登录/目录 scope 不能通过放宽原工作区 scope 的校验实现；需要单独的能力协商与验证。deep link 只承载受校验的路由和一次性流程标识，长期凭据不能通过 URL 或 renderer 转发。

## 6. 会话和生命周期不变量

```mermaid
flowchart LR
    Picker[现有服务和模型选择器] --> Source[版本化来源引用]
    Source --> Session[正常会话创建和恢复]
    Source --> Apps[现有 App connections]
    Session --> Proxy[本地协议代理]
    Apps --> Proxy
    Proxy --> Credentials[原生动态凭据解析]
    Credentials --> API[公开服务接口]
```

同一会话只由一个来源持有认证；`account_id` 与动态来源的互斥关系在生产创建/恢复边界验证。所有 continuation 路径也必须携带引用，不能仅保存在前端 atom。

路由、model、target、auth scope 按同一来源顺序恢复：明确的本次输入 → 当前 session → 持久化 session → 可执行恢复错误。某个字段无法恢复不能单独取一个个人账号默认值凑齐。

凭据更新合并并发请求，缓存有数量与过期上限；目录查询仅在相关界面/事件需要时刷新，隐藏页面不持续轮询。启动、取消、撤销与退出有界，已退休连接的晚到结果不能重新登记为有效。

一旦请求已经产生输出或工具调用，不自动从客户端重放整个调用。会话历史保存在正常历史存储中；不能依赖上游独有的缓存/文件/响应句柄来承诺通用恢复。不同原生应用的延续与状态能力分别测试。

## 7. 实施批次

每批尽量控制在约 20 个逻辑文件内，涉及共享 wire 类型的 Rust/TypeScript 同批更新。每批建立真实消费者，避免只增加未接入的抽象。

| 批次 | 内容                                                       | 验收出口                                                      |
| ---- | ---------------------------------------------------------- | ------------------------------------------------------------- |
| C0   | 明确公开协议、完成标准、旧数据读取边界；排除不需要的迁入项 | 共享 fixtures、入口矩阵与复用清单可评审                       |
| C1   | 授权模块、来源引用、RPC、动态认证注册/退出与错误状态       | 无已有记录也能登录；重放/跨连接/未知版本失败；秘密不进入 IPC  |
| C2   | 服务目录、首次激活/账户操作恢复、现有模型选择器            | 同一选择能跨登录/恢复保留；目录错误可重试，不显示空列表假成功 |
| C3   | 正常 session 创建、执行、继续、持久化恢复和路由所有权      | 真实对话/工具调用可用；切换来源不改写旧 session；重启能继续   |
| C4   | 原生配置、启动、冲突/恢复和必需的历史位置适配              | 每个支持目标真实使用成功，配置恢复不覆盖外部编辑              |
| C5   | 平台/协议/退出/撤销验收，文案及发布能力声明                | 把实际支持的 OS、客户端版本和剩余限制记录在实施 PR            |

## 8. 验证要求

| 场景                           | 结果                                             |
| ------------------------------ | ------------------------------------------------ |
| 新用户、无旧记录               | 可发现服务并完成首次使用，不先创建旧购买对象     |
| 目录分页/空/加载失败           | 状态准确；失败能重试；不会丢失已保存选择         |
| 模型或目标不兼容               | 使用公开能力正确限制，未知值默认拒绝             |
| 登录取消、重复回调、旧回调晚到 | 不重复激活，不覆盖新连接                         |
| 多请求同时需要更新认证         | 一次有效更新可共享，过期/撤销的结果不能继续使用  |
| 持久化来源恢复                 | 新建、继续、重开、重启读同一字段，不回退个人账号 |
| 标准对话和本地工具             | 真实输出进入正常历史；未注入额外远程 MCP         |
| 配置冲突/客户端卸载/重新安装   | 状态与恢复操作准确，不覆盖用户改动               |
| 关闭窗口/完整退出/重启         | 后台与退出行为可区分，本地路由及恢复结果真实     |
| 旧协议/未知新版本              | 已发布行为不变，新能力只对明确支持客户端开放     |

实现阶段按最终修改范围运行：`pnpm typecheck:fast`、`pnpm test -- <changed test paths>`，以及 `src-tauri` 下受影响 crate 的 `cargo test`/`cargo clippy`；Market 模块开启与关闭都验证 init/退出路径。新 E2E 必须从真实 UI 操作入口触发，测试 helper 只能用于准备或读取断言。

原生业务验收需要实际构建、实际客户端和真实请求，逐项记录 macOS/Windows、客户端名称和版本。编译成功、deep link 回执、卡片出现都不能替代成功对话与恢复行为。

## 10. 交付边界

本 PR 是客户端方案评审。主要待定项为公开 contract 版本和字段、已发布数据的兼容范围、逐客户端能力集合；这些确定后再实施。

公开仓库仅保存客户端必要代码、公开协议与相应合成测试数据。客户端不实现服务器的业务策略或管理系统；PR 描述、提交说明、fixture 与日志也遵守同一边界。

新实现从最新 develop 开始，#1846 保留为参考直到替代方案完成。发布前补真实平台验收并按实际能力开放；本次不修改旧 PR 状态或发布任何客户端版本。

## 钱包模式协议更新

启用提交 `billing_mode: wallet`，不提交套餐预算；access 的预算字段在该模式为空，保留历史有限额解析。目录请求声明 `wallet_billing=1` 并读取公开能力列表，服务未更新时禁止新启用。市场确认后直接唤起 ORG2，真实 workspace 用于复用已授权连接；首次登录仍走正常授权。没有新增轮询或自动改写历史 access。详细兼容与待测流程见客户端交接文档。
