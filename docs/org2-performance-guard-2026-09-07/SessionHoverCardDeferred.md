# SessionHoverCard deferred content lifecycle review

The small SessionHoverCard wrapper now obtains its substantial content module only after HoverCardBase opens the card. The existing 500ms opening delay and singleton portal owner are unchanged. A shared code loader caches one resolved component and one in-flight import; it never caches session data. A loading or failed import renders a localized HoverCardPanel fallback. Failures release the in-flight entry, allowing a subsequent hover to retry without a periodic retry loop.

## Lifecycle matrix

| Dimension        | States considered                                 | Evidence or applicability                                                                                                                                                                                                                              |
| ---------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| App              | start, idle, active, shutdown                     | No content import on mounting idle triggers; import after intentional hover; unmount cleans the continuation guard. The application owns normal module-code lifetime.                                                                                  |
| Document         | visible, hidden, focus return                     | No added polling, timer or visibility listener. An already-started chunk import is not cancelable and may finish after close or document hiding; it cannot mount closed content. Actual hidden-document/WebView timing was not exercised.              |
| Network          | online, offline, recovery                         | Pending import is single-flight; failed import displays an alert, then subsequent hover can retry. Deferred success/rejection fixtures cover the owner logic; actual Webpack transport/network recovery was not exercised.                             |
| Identity/scope   | account, endpoint, org, session changes           | No identity data retained in the module cache. Rendered content still owns its existing session lookups; switching hover owner during load mounts only the new owner. Account/endpoint and deletion lifecycle are unchanged and not separately tested. |
| Instance         | primary, secondary                                | Code cache is module-local within each webview; no cross-instance persistence or channel added. Physical multi-instance execution was not run.                                                                                                         |
| Source/transport | provider ingestion, upload, reconnect             | Not applicable: no provider, source, persistence or sync path changes.                                                                                                                                                                                 |
| UI               | brief hover, delayed load, close, reopen, failure | All covered with actual HoverCardBase mouse events and fake timers in jsdom. Portal geometry remains source-identical; real layout/latency is unmeasured.                                                                                              |

Architecture coverage: layers 2/6/7 establish the lightweight loader/rendering seam and one code-cache owner; layers 3–5 preserve names, card identities and the original delay defaults; layer 9 keeps content initialization at visible mount and rejects closed completions. Layer 1 focused tests/lint and full TypeScript checking pass. The isolated branch has a static-import regression covering the trigger-to-details boundary. Production bundle analysis was not run for this independent change. Layers 8 and 10 have no applicable wire or resolver changes.
