# Channel Inbox Realtime and performance acceptance

## Scope and environment

Run on September 24, 2026 (05:03–05:22 UTC September 25). The production frontend combined #2150 at `1950bae92b` with #2151 at `6d9cbc19e6`; the native shell was develop `8f13b1b52e`. Two isolated macOS Tauri apps had separate homes, WebKit storage, provider roots and ports. The endpoints were loopback-only. No production service, schema, cloud resource or runner configuration changed.

The dedicated stack used PostgreSQL 17.11, PostgREST 12.2.12 and official `supabase/realtime:v2.134.10`. Realtime tenant migrations created the real `realtime.messages`, `realtime.send`, partitioning and logical-replication infrastructure; all ORG2 migrations through 0037 and plan entitlements were then applied. A reverse proxy forwarded actual WebSockets without synthesizing broadcasts. Fixture `/auth/v1/user` responses and an anon-key alias were local prerequisites. RPC and private-channel authorization used signed JWTs and the production database functions/RLS.

The first setup attempt lacked required Supabase roles, a usable anon JWT and the `wal2json` output plugin/configuration. Those were corrected in this disposable stack. The resulting setup/reconnect traffic is excluded from the healthy idle window. One 20-request load-fixture attempt hit a proxy keep-alive `ECONNRESET`: 19 writes were confirmed in SQL. The subsequent 1,000-request load phase used real PostgREST directly and completed in 1.04 seconds. This was a fixture-proxy failure, not a product API rejection; both attempts are included in the final ledger.

The test-window frontend log audit found no unexplained destructive action or watchdog recovery. After acceptance, both native apps were explicitly quit and their attributed native/WebKit processes disappeared; the other user/task instances remained running. Task-owned loopback services were stopped after the final ledger readback.

These are local isolated-instance results, not two physical computers, hosted OAuth/refresh-token acceptance, OS notification-center delivery, or a cross-platform/network-latency claim.

## Resource measurements

`proc_pid_rusage` sampled the two native processes and their six attributed WebKit helpers, excluding other running instances. CPU is process CPU time divided by elapsed wall time (100% = one core). Physical footprint and resident RSS are reported separately in [the measurements](realtime-performance-measurements.json); virtual address reservations are not counted as used memory.

The retained footprint is a **measured unresolved memory issue**, not an unmeasured checklist item or a proven linear leak. `vmmap` attributed about 394.5 MiB in A and 419.8 MiB in B to allocated WebKit Malloc bytes, with only 6–7% fragmentation. A large share was compressed/swapped: a low resident RSS does not establish low retained usage. The second cycle group ended below its starting footprint, which does not support monotonically increasing leakage, but does not explain the several-hundred-MiB baseline or activity peaks either. Allocation ownership at the JS/DOM boundary still needs profiling; no guessed UI filter or cache deletion is used as a fix.
