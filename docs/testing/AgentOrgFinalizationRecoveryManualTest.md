## 1. 暂停后自动交付

### 准备与操作

1. 新建一个至少含协调者和两名成员的团队，所有成员选择 `codexharry / gpt-5.6-luna-medium`。
2. 在全新项目目录发送：

   > 请创建两项独立任务：成员 A 新建 `pause-a.txt` 并写入当前时间与任务说明；成员 B 新建 `pause-b.txt` 并复核两个文件是否存在。必须通过正式任务分派，两个任务都完成后提交最终报告。

3. 确认两项任务已经创建并至少一名成员处于工作中，点击团队面板的“暂停”。
4. 等界面显示已暂停，再点击“恢复”。
5. 从这一步开始不要再发送任何提醒，等待成员完成。

### 通过标准

- 原来的两项任务继续存在，没有被重新创建。
- 两项任务完成后，协调者自动进入正式交付并保存最终报告。
- 团队最终为 Idle。
- 不需要你补发“继续”“任务完成了吗”或“请交付”。
- 旧的“成员空闲”消息不会制造一个没有实际工作的额外模型轮。

### 失败判据

- 所有任务已完成，但 60 秒后仍没有最终报告且团队一直等待。
- 恢复后同一任务重复创建或旧执行继续写文件。
- 必须由你发一条新消息才开始交付。

## 2. 结算期间保留草稿

### 准备与操作

1. 创建一项能在约 1 分钟内完成的团队任务，并要求最终报告列出实现、测试和文件清单。
2. 在成员仍工作时，在输入框提前输入但不要发送：

   > 报告结束后，请再解释 pause-a.txt 的用途。

3. 等界面出现“正在完成本轮工作，完成后可以继续发送”的结算提示。
4. 检查输入框仍可编辑，继续补上“并说明由谁创建”。
5. 按一次 Enter，并点击当前可见的控制按钮时注意它只能是 Stop，不能把草稿作为新消息发出。
6. 等最终报告保存后，再手动发送这段草稿。

### 通过标准

- 结算提示在群聊、协调者私人会话和成员私人会话中一致。
- 输入内容在结算中和结算结束后都完整保留。
- Enter 不产生用户消息、排队项或模型请求。
- 报告保存后发送能力恢复，手动发送只产生一条新请求。

## 3. Stop、失败和 Retry 后的输入状态

### Stop 与 Retry

1. 重做第 2 组，在结算提示出现后输入一段未发送草稿。
2. 点击 Stop，等待报告状态明确变为已停止或失败，并出现 Retry。
3. 确认草稿仍在，且普通发送入口已经恢复。
4. 不发送草稿，点击 Retry。
5. 确认新的报告尝试开始后再次出现结算提示，草稿仍在且不能发送。
6. 等 Retry 报告保存，只应有一个新报告尝试，成员任务不能重跑。

### 保存失败

正常用户操作不一定能稳定制造磁盘保存失败。如果测试期间自然发生保存失败，检查团队回到可输入状态、失败证据仍可见、Retry 可用；若未发生，记录“手测未命中，自动故障注入已覆盖”，不要破坏数据库来制造失败。

## 4. 被拒绝请求恢复

### 准备与操作

1. 让团队开始一个有正式任务但尚未形成最终凭证的旧工作。
2. 在旧工作仍未关闭时发送一条明确要求创建独立新任务的消息，例如：

   > 这是另一项独立工作。请现在创建新任务，让成员新建 `later-request.txt`，内容为 `manual recovery`。

3. 如果协调者的 Task 创建被旧工作保护拒绝，检查工具卡明确写出“任务未创建”“不会自动重试”，并出现“恢复为草稿”。
4. 刷新应用或切换到其他会话再回来，确认入口仍存在。
5. 先在输入框输入 `我正在编辑的新草稿`，再点击“恢复为草稿”。
6. 在预览中检查现有草稿和原请求，先点取消；再次打开后点追加。
7. 等旧工作正式结束后，检查合并后的草稿，只手动发送尚未完成的部分。

### 通过标准

- 原请求来自准确的用户消息，包括原文字、图片、引用和成员提及；不能变成模型回复或任务标题。
- 输入框已有内容或只有图片时，必须先预览，不能静默覆盖。
- 点击恢复只填入草稿，不发送、不重放原执行、不自动创建任务。
- 手动重发后只创建一次新任务。
- 如果旧记录没有准确来源，界面说明无法恢复，不拿相邻消息代替。

## 5. 正常工作不受误拦

1. 新建团队并开始普通工作。
2. 在结算前依次做三件事：补充当前任务要求、回答成员澄清、使用任务取消控制。
3. 再用 `@成员` 发送一条直接问题。

通过标准：这些操作在正常工作和等待成员阶段都可用；只有最终报告处于待生成、生成中或保存中时，用户消息才被拦截。暂停、归档等原有规则继续按各自提示工作。

## 6. 已知长历史导航失败

这项用于记录现状，本次不要求测成通过，也不要因为它失败而修改其他验收结果。

1. 在同一团队群聊积累至少 57 个真实执行轮，混合很短和较长的回复，并保持一些旧轮为折叠状态。
2. 找到一个当前私人历史虚拟列表尚未挂载的旧群聊回复。
3. 点击“查看执行详情”，观察是否准确切换到对应成员和对应执行标题。
4. 再执行刷新、加载更早历史、改变折叠状态后重复一次。

记录以下任一失败：跳到近似轮次、目标标题没有进入视口、跨页后找不到目标、晚到布局变化后定位漂移。自动 E2E 会保留这个场景的独立失败结果，本次不把它写成已修复。
