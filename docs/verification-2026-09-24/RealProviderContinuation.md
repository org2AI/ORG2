# Real provider continuation acceptance

## Environment and scope

Two isolated ORG2 macOS desktop instances on one host, two fresh test identities, and one test organization. This is not a two-physical-machine result. Production cloud state was read for the fleet ledger; writes were limited to the test organization. Native provider accounts used access/ID tokens without rotating refresh tokens. The live build combined snapshot commit `2b6d54be5a`, storage isolation `17ada499d1`, and a minimal Codex auth-payload fix discovered during this run. Published design and verification text remain English.

## Positive evidence

1. Native Codex with `gpt-5.6-luna` produced `LIVE_LUNA_BASE_20260924` in desktop A. The session reached completed.
2. The normal sharing controls selected full replay. The production sync engine uploaded five initial events at epoch 1. The cloud gzip payload was decoded and verified; desktop B opened the actual shared row and rendered the exact answer.
3. B submitted through the rendered shared-conversation composer using Test Luna. A native Codex child completed, correctly recalled the base marker, created `live-luna-proof.txt`, and returned `LIVE_LUNA_CONTINUED_20260924` plus a Markdown file link.
4. The conversation RPC returned the real assistant reply, tool event, and terminal event. A rendered the same continuation. A then submitted a real owner follow-up; the model returned `LIVE_LUNA_OWNER_RETURN_20260924` and correctly recalled B's continuation marker. B rendered this answer after focus resumed.
5. The automatic file publisher uploaded 30 bytes with SHA-256 `404724bd21ad7c319505335487d7e2817478308da4f20b09c7a9f357172b4f7c`. The authenticated cloud download matched the model-generated bytes. B's imported-session Markdown link opened the shared-file viewer. The initial preview passed; reopening after the owner follow-up failed as detailed below.
6. SQLite read-back on B showed an uploaded receipt with NULL bytes and an empty file outbox. No synthetic assistant events or direct file-upload RPC were used to create this success.
7. The fleet baseline contained 3,506 rows, including 768 historical rows above epoch 3. The final scenario added one test session; all pre-existing rows were unchanged. The test session remained full replay, undeleted, epoch 1, and grew from 5 to 13 events as real turns landed.

Production DOM controls were activated through WebDriver DOM clicks and the editor's input mechanism. Setup helpers supplied isolated accounts, cloud identity, repository selection, and deterministic sync-pass boundaries. The first cloud assertion incorrectly searched compressed bytes without decoding; the corrected assertion decoded the gzip payload. The initial secondary account cache was stale after a direct native account write; the rendered model refresh control resolved it. Neither is claimed as a production sync failure.

## Defects and limitations

- **Codex bearer-only auth shape:** the generated `auth.json` omitted a required refresh-token string. The CLI ignored authentication and returned 401. An empty string fixed the live requests without cloning refresh authority. A separate focused PR adds this correction and narrowly repairs existing malformed profiles.
- **Claude Code remains blocked:** Auto Detect found an expired/revoked native OAuth login; the provider returned 401. A preliminary launch also escalated an unavailable native history file to the global App error surface. This launch had not refreshed the account-selection cache, and its persisted model was null, so it does not establish behavior for a correctly selected Claude account. The producing history resolver propagates missing-path errors into the preview RPC; the global error escape is an open defect, not a successful recovery.
- **Path lookup becomes ambiguous after owner continuation:** reopening B's shared-file viewer after A continued returned HTTP 400 `ORG2_FILE_AMBIGUOUS`. The server rejects path-only lookups when multiple uploaders own that path. Original artifact lookup by ID still returns valid bytes. Read-back confirmed B's original receipt and A's later replay upload have distinct file IDs and uploader identities but identical 30-byte hashes. A's materialized native history rebased the old assistant event ID/timestamp; the replay publisher treated it as A's local artifact and uploaded it again. The viewer supplies no revision/uploader identity; file provenance must be retained through continuation and replay. Moving the local fixture file exposed this on re-open, but cannot cause a server-side multiple-uploader error. This fails the attachment lifecycle cell; no cloud data was deleted or selected by a newest-version workaround.
- **Owner view loses remote file origin:** a guest-generated Markdown file link rendered in the original owner's local transcript opens a local editor path. `SessionCommentsContext` supplies the shared-file interception scope only for imported sessions. This passed local navigation on one host because the file existed there; it does not meet the two-machine contract for files generated by teammates. Imported receiver scope and authenticated cloud bytes work. The owner/per-turn origin boundary requires a separate source-level fix.
- **Terminal diagnostics:** B logged two dropped-terminal diagnostics for its native continuation child because the visible session was the imported root. The shared conversation did receive `task_completed` and returned idle. Exact backend-terminal-to-visible-idle latency was not instrumented, so the five-second acceptance cell is uncovered.
- **Screenshot evidence unavailable:** WebDriver PNG capture returned a largely black surface, despite readable DOM content. Those images are not accepted as visual proof.
- **Performance remains blocked:** this small-file real-model run does not resolve the earlier 585 MiB active snapshot RSS observation. The hidden cold-boot watchdog defect recorded in the storage-isolation report also remains open.
- `/compact`, cache wipe/rebuild, old-to-new persistent-state upgrade, two repeated cold boots with real cloud turns, and a separately rooted B-to-A scenario were not rerun here. Earlier synthetic snapshot acceptance does not substitute for these real-provider cells.

The new evidence establishes live provider continuation and automatic artifact publication, not complete sharing acceptance or a claim that all reported issues are fixed.
